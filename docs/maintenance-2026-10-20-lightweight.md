# 2026-10-20：恢复简洁、轻量和上下文友好的主线

对应版本：v0.3.2。作者补充：原始设计还包含“简洁和轻量化以及对上下文友好”，意味着快速、简洁、高效。这部分现在写入 [设计原则](DESIGN.md)，作为后续维护依据。

本文保留 v0.3.2 的离线测量。后续真实评测发现过早移除读取结果会导致反复读取，并在 v0.3.3 加入旧读取摘录与按坐标重读；服务实际 token、耗时及失败样本见 [真实测试报告](maintenance-2026-10-20-real-evaluation.md)。

## 开销从哪里来

检查 v0.3.1 发现：普通执行任务第一轮只提供规划工具，即使是创建小文本文件也必须先生成计划；开发模式虽已绕过此限制，但附带无条件的多源文件、架构文档和新网页浏览器交互要求。通用提示词为 2,925 字符，每次请求重复发送；历史思考只在请求超过硬预算时才省略，较长的历史工具结果在未超限前也全部重发。

这些规则增加了请求轮数、输入和输出量。模型生成本身也可能很慢，尤其会输出长思考的模型；运行时请求精简与模型生成速度需要分别测量。

## 本次精简

- 所有任务都能立即使用授权工具；规划和阶段声明按需使用。普通问题可以直接答复，问候不携带工具 schema。已声明计划仍进行完成核对，阶段回溯继续可用。
- `reasoningHistory: auto` 默认省略请求副本中的历史思考，即使尚未超限。本地完整思考和记录不删除；需要完整思考重放的服务可使用 `reasoningHistory: full`。这是相对于 v0.3.1 的默认行为调整。
- 工作上下文采用 **32,000 保守估算单位**的软目标，提前压缩较早的助手/工具过程。全部系统与用户消息、最近完整工具事务和最后一组消息保留。必要内容超过软目标时允许保留至模型硬预算，超过硬预算仍明确停止核对，不截断必要工具参数或结果。
- 通用提示词缩至 **1,138 字符**；开发说明也缩短。工具参数与限制主要由现有 schema 说明，减少重复叙述，不新增模型摘要请求。
- 删除新项目一律要求至少两个源文件、README、架构文档和网页交互的隐含验收。实际文件、写入后内容核对、开发任务最终修改后检查，以及用户明确指定的文件、测试和计划验收仍保留。小项目可以只有一个文件。
- 显式文件名识别增加 Markdown/文本路径；无计划的执行任务也核对本轮是否真实写过指定文件，已有同名文件不能替代本轮交付。
- Web 说明思考与旧过程消息的精简数量，显示范围限于当前轮次。

软目标不是精确 token 数、总对话长度或严格的固定请求上限。它包含工具定义；保留完整工具事务有时会使请求大于软目标。历史原始记录可供审查，模型本轮不会自动获得所有旧过程；开发模式仍带有依据真实记录生成的有界项目状态，需要旧内容时应重新读取或复用现有读取结果。

## 相同输入的请求体积对照

新增 `scripts/measure_context.py`，只用固定的合成文本和原生工具定义构造请求，不读取真实配置或用户文件，不连接模型。修改前在 v0.3.1 提交 `f1747b8` 的实现上保存基线，再用相同脚本与输入测量新实现。计量使用现有保守 UTF-8 估算，**不能当成服务实际 tokenizer 的 token 用量或生成耗时**。

| 场景 | v0.3.1 | v0.3.2 | 请求体积估算减少 |
| --- | ---: | ---: | ---: |
| 两轮工具结果，含 16,000 字符历史思考；原本未超预算 | 35,476 | 17,643 | 50.27% |
| 20 轮文件读取历史，原本未超预算 | 59,186 | 24,279 | 58.98% |

第二组保留 13 条请求消息，本地仍有全部 43 条；系统和用户要求、最近调用及结果配对保留。完整对照与边界见 [测量报告](evaluations/2026-10-20-lightweight.json)。

原失败记录再次只读回放：请求估算从 v0.3.1 自动整理后的 43,948 降为 **15,690**，原始记录内容校验不变，系统/用户要求与最近工具 ID 配对保留，真实模型请求为零。这只是旧记录模型输入视图的验证，没有补做原游戏或测量真实后续生成。

本地重测：

```powershell
$env:PYTHONPATH='src'
$env:PYTHONUTF8='1'
python scripts/measure_context.py
```

## 验证及边界

本地完整测试 **496 项通过**，Ruff、JavaScript 语法与差异空白检查通过。新增/调整场景验证：

- 简单问题一次模型请求直接回答；问候一次请求、不携带工具 schema。
- 小文本任务第一轮真实写文件，第二轮结束，无规划调用。
- 单文件 Python 项目实际写入并检查，不要求新增源文件或架构文档。
- 明确要求的架构文件缺失、只口头声称写过文本文件、检查失效或用户修改被覆盖等情况仍不能通过交付。
- 未达硬预算时就整理历史；用户与系统要求、完整最近事务、原始持久记录保留。必要内容大于软目标但小于硬预算时可继续。
- 完整思考重放的显式配置、真实长思考后续文件交付、原有失败/恢复/权限场景继续通过。

这次没有调用真实模型做速度或成本评测，不能给出“所有任务快多少”或实际 token 节省比例。可证明的是默认流程减少了不必要的规划往返，固定输入的请求体积明显降低。模型服务的生成速度、思考设置和具体任务选择仍会影响实际体验；后续测量应同时记录真实 token、模型请求次数与完成耗时。
