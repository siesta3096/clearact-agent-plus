## 最值得保留的工程案例

### 1. 读过文件，并不意味着后续可以永远跳过

早期重复读取保护逐渐加入文件版本和读取范围判断：相同内容可以复用，文件改了就重新读；只读过前一段，不能认定后面的内容已读；越过文件末尾也不能误判为已有范围。

进一步处理了回溯保留阶段的结果复用、跨后续对话复用，以及缓存不能绕过当前权限。复用时给模型实际内容，而不是一句“已跳过”。

证据：[test_runner.py:129](../tests/integration/test_runner.py#L129)、[文件变化:164](../tests/integration/test_runner.py#L164)、[缓存权限:255](../tests/integration/test_runner.py#L255)、[范围复用:343](../tests/integration/test_runner.py#L343)、[EOF:382](../tests/integration/test_runner.py#L382)、[回溯复用:746](../tests/integration/test_runner.py#L746)。

### 2. 反复搜索，并不等于调查更充分

增加本地资料优先、搜索总量和连续搜索限制；连续搜索后要求打开来源；近似查询复用，但年份变化不能当同一次搜索；搜索服务整体失效或网页已失败时避免反复重试。

证据：[连续搜索:400](../tests/integration/test_runner.py#L400)、[近似查询:552](../tests/integration/test_runner.py#L552)、[先读附件:591](../tests/integration/test_runner.py#L591)、[失败页面:1201](../tests/integration/test_runner.py#L1201)、[失效搜索服务:1318](../tests/integration/test_runner.py#L1318)。

### 3. 回到旧阶段，不能顺便覆盖用户后来的修改

回溯前展示影响；核对快照和真实写入目标；只有当前文件仍与 Agent 最后写入一致时才还原。用户后来改过的内容会保留，并提示冲突。预览到确认之间文件再变化，也会被检测。旧分支完整归档，可以回看。

这是当前最完整、最容易用演示和测试证明的设计之一。

证据：[恢复逻辑:306](../src/clearact/webapp.py#L306)、[目标校验:284](../tests/unit/test_webapp.py#L284)、[保护用户修改:315](../tests/unit/test_webapp.py#L315)、[预览后变化:342](../tests/unit/test_webapp.py#L342)、[分支归档:454](../tests/unit/test_web_recovery.py#L454)。

### 4. 工具失败或任务停止之后，记录也要闭合

失败动作不再写成功 checkpoint；用户拒绝、超时、取消、预算耗尽都保留明确结果；同一批工具调用停止时为未完成动作补齐结果，避免上下文出现“有调用、无结果”。停止流程等待清理，再读磁盘最新状态，避免覆盖刚保存的进展。

证据：[失败结果:1265](../tests/integration/test_runner.py#L1265)、[取消:1368](../tests/integration/test_runner.py#L1368)、[预算耗尽:1425](../tests/integration/test_runner.py#L1425)、[停止清理:374](../tests/unit/test_web_recovery.py#L374)。

### 5. 长上下文不仅要缩短，也要保持协议合法

统计消息、工具定义、参数等输入负担；按工具调用及全部结果为一组压缩；拒绝孤立或缺失的工具结果；不把旧工具返回提升为系统指令；必要内容超出预算则明确失败。

不过，中途新增约束的保留仍有缺口，见后文。

证据：[context_budget 测试](../tests/unit/test_context_budget.py)、[分组与压缩](../src/clearact/context/compact.py)。

## 本次发现的实际问题和限制

### A. Agent 的四类浏览器动作会报错：已复现，适合先修

位置：[computer_use.py:395](../src/clearact/tools/computer_use.py#L395)。

当前调用为 `session.control(action, **arguments)`，而 `arguments` 自身包含 `action`。`BrowserSession.control` 又把 `action` 当作命名参数，因此重复传值。

本地用假会话分别调用 `press`、`scroll`、`back`、`reload`，四者均出现 `TypeError: ... got multiple values for argument 'action'`。无需浏览器、网络或模型即可复现。

影响范围是 Agent 工具的这四个动作；人工侧栏控制走另一条调用路径。现有浏览器测试覆盖权限、URL、未打开会话和脱敏，没有覆盖这些动作转发。

建议：去掉重复参数，补动作转发测试，再做一次隔离浏览器中的实际导航与滚动验证。

### B. “不要联网”的部分自然表达被误判：已复现

位置：[research_strategy.py:5](../src/clearact/runtime/research_strategy.py#L5)、[策略分支:62](../src/clearact/runtime/research_strategy.py#L62)。

| 输入 | 实际分类 | 问题 |
| --- | --- | --- |
| 别联网，只根据我给的内容整理 | research，策略没有搜索总限额 | 否定未识别，“联网”触发主动联网 |
| 不要浏览网页，只用现有资料 | research，策略没有搜索总限额 | 否定未识别，“网页”触发主动联网 |
| do not use the internet | balanced，策略允许 6 次搜索 | 未识别禁止联网 |

这里的“没有搜索总限额”指资料策略，整个运行仍有工具调用预算。此复现证明意图分类错误，不证明独立权限政策被绕过，也不证明任务已经实际发出网络请求。

建议：建立否定、条件、跟进修改的语句案例；将明确的会话约束与可变资料策略分开表示，不能单靠少量关键词。

### C. 长会话压缩可能丢掉中途补充的限制：已复现

位置：[compact.py:51](../src/clearact/context/compact.py#L51)。

压缩强保留系统消息、首条/最新用户请求及最新工具事务。中途的用户消息不一定保留。

本次用实际 `ContextBuilder` 构造：创建报告 → 用户补充 `Do not overwrite existing files.` → 12 条较长助手历史 → 用户要求继续。触发预算压缩后，用户消息只保留创建报告和继续请求，中间的禁止覆盖限制被移出模型输入。

这是输入丢失的复现，尚未验证真实模型随后是否会覆盖文件；独立权限仍存在。但它说明持续约束没有稳定的保留机制。

建议：区分长期有效约束、已被替代的要求、当前目标和过程信息；压缩前后验证约束仍在，并明确用户何时可以撤销旧约束。

### D. 完成检查是软提醒，还没有结构化验收：假模型流程已复现

位置：[runner.py:220](../src/clearact/runtime/runner.py#L220)、[完成判定:246](../src/clearact/runtime/runner.py#L246)。

审查用固定模型响应声明“至少打开两个来源”的 research 阶段，进入阶段后不做搜索/抓取，连续返回完成。系统给一次补做机会，最终仍将 run 标为 completed，同时阶段标 needs_review 并保留警告。

因此不能说没有完成检查；准确描述是“已有检查和需核对状态，但文本完成条件尚不能机器验收”。

建议：为特定任务引入可验证条件，例如应有文件是否存在、必需操作是否成功、来源是否确实打开；区分完成、部分完成和需复核。优先验证可检查的产物，不急于通用评判任意答案质量。

### E. 跨重启可以续接历史，但不能自动恢复原执行：隔离状态模拟已复现

位置：[内存任务和审批:48](../src/clearact/webapp.py#L48)、[checkpoint 存储](../src/clearact/storage/checkpoint_store.py)。

任务、活动 Run 对象和待审批 Future 在内存中；checkpoint 目前追加保存成功动作，没有读取和重放流程。没有启动时对旧运行状态的对账。

在临时目录保存 WAITING_APPROVAL 状态，再以空活动任务/审批字典读取 API：记录仍为 waiting_approval，但没有可见审批，也没有活动任务。这模拟了进程丢失执行状态后的遗留记录，不是实际杀进程测试。

用户能手工停止或续接话题，保留原目录、模型和预算，但这不等于从原待批准动作精确恢复。

建议的第一步是启动时识别遗留运行，标为“已中断”，提供核查后的继续入口。之后再处理可能重复的副作用、动作幂等和回溯中断；不要一开始承诺自动重放所有外部操作。

### F. 其他已经确认的边界

- 文件、任务记录、事件和分支档案不是一次跨文件事务。回溯中途崩溃可能产生部分恢复状态，这是静态风险，未进行崩溃注入复现。
- 网络调用和浏览器/MCP 的外部副作用只能提示，不保证撤销。
- 上下文预算使用 UTF-8 字节数作为保守估计，不是真实 tokenizer；工具定义很多时会占据预算。没有进行大规模 MCP 工具场景实测。
- 安装目前以源码/可编辑安装为主：CLI 用模块文件的上两级目录找配置，配置 YAML 位于包目录之外。普通 wheel 的配置定位需要单独验证；本次环境缺少 hatchling，没有构建 wheel，不能把这一项写成已复现的安装失败。
- [pyproject.toml](../pyproject.toml) 仍为 `0.1.0`，[CHANGELOG](../CHANGELOG.md) 集中在 Unreleased，本地没有 Git 标签。未查询远端 Release，不据此判断远端是否发布过。

## 接下来值得做什么

建议围绕一条主线维护：**长任务执行可靠性与安全恢复**。当前已有基础，也有明确缺口，不依赖先获得大量用户。

| 顺序 | 工作 | 为什么值得做 | 可交付证据 |
| --- | --- | --- | --- |
| 1 | 修浏览器动作转发和禁止联网漏判，补对应案例 | 缺陷已经复现，范围明确，能直接改善现有能力 | 复现、修复提交、回归测试、一次实际演示 |
| 2 | 固定一组代表性任务和失败场景 | 让“可用”和“改善”有可重复的判断依据 | 输入、预期、运行结果、失败原因；真实模型层记录模型/配置/耗时/工具次数 |
| 3 | 做跨重启的遗留任务状态对账 | 先解决“记录说在运行、实际没有任务”的可信度问题 | 中断前后记录、用户看到的状态、继续入口与集成测试 |
| 4 | 选约束保留或结构化验收中的一个深入 | 都有明确技术问题；同时做会扩大范围 | 压缩前后约束案例，或产物/必需动作的验收案例 |
| 5 | 整理版本和案例入口 | 让已有维护能被快速核实 | 简洁首页、版本说明、三个工程案例、短演示 |

真实模型评测与固定返回的运行时测试需要分层：前者衡量实际任务表现，后者定位执行系统是否遵守规则。前后比较应保留相同任务、输入及尽量一致的模型配置，并记录失败，不编造成功率或使用人数。

当前不需要同时扩展更多 Provider、主题和工具种类来增加功能数量。先把已有任务执行链条做得可信，可以形成连续的维护记录。
